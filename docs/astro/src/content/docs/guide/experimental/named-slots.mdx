---
title: Named Slots
description: Experimental named slots for multiple content insertion points.
---

A `slot` is a named insertion point where a component renders content supplied by its user.
It generalizes the built-in `@children` placeholder: instead of a single anonymous block of children, a component can declare several slots and place each one at a distinct location in its own layout.

> **Note**: named slots are experimental and subject to change.
> Enable them with the `named-slots` [experimental feature](../overview/).
> Tracking issue: [slint-ui/slint#6258](https://github.com/slint-ui/slint/issues/6258).

## Declaring a slot

Use the `slot` keyword inside a component to declare a slot, then render it at the desired location by writing the slot's name as an empty element.

```slint
export component Base inherits Rectangle {
    slot header;
    slot footer;

    VerticalLayout {
        header {}      // render site for the `header` slot
        @children      // the default slot
        footer {}      // render site for the `footer` slot
    }
}
```

A declared slot must be rendered exactly once.
`@children` continues to work as before and represents the default, unnamed slot.

## Assigning a slot

The user of a component fills a slot with the `<<` operator, naming the slot on the left and the content on the right.
Content that is not assigned to a named slot goes to `@children`, as usual.

```slint no-test
export component App inherits Rectangle {
    Base {
        header << Rectangle { background: blue; }
        Text { text: "Main Content"; }   // goes to @children
        footer << Rectangle { background: gray; }
    }
}
```

Assigning an untyped slot is optional.
An unassigned untyped slot renders its [default content](#default-content), or nothing if it has none.
[Scalar typed slots](#typed-slots) require a supplied component.

## Default Content

Give an untyped slot or collection slot default content with `<<` in its declaration.
The component shows the default until a caller assigns the slot.
An assignment replaces the whole default, including its layout constraints.

```slint
export component Panel inherits Rectangle {
    slot heading << Text { text: "Untitled"; }
    VerticalLayout {
        heading { }
        @children
    }
}

export component App inherits Window {
    VerticalLayout {
        Panel {
            Text { text: "Shows the default heading"; }
        }
        Panel {
            heading << Text { text: "Project"; }
            Text { text: "Details"; }
        }
    }
}
```

Assign `{ }` to remove the default content without replacing it:

```slint no-test
Panel {
    heading << { }
}
```

The default content is a single element.
Wrap an `if` or `for` in an element to use it as default content.
Default content can't contain slot placeholders or `@children`.
A `Tab` in a `TabWidget` and a `Menu` in a `ContextMenuArea` or `SystemTrayIcon` can't be default content;
declare them as children instead.

Replacing the default removes its elements, so references to them from outside the default content are errors:

```slint no-test
component Foo inherits Rectangle {
    slot bar << label := Text { text: "Default"; }
    Text { text: label.text; }   // error
    bar { }
}
```

References between elements inside the same default content are allowed.
For shared state, declare a property on the component and bind both the default content and other elements to it.

A slot that's forwarded to another component's slot can't have default content.
Set the default on the target slot instead.
Scalar typed slots don't support default content yet.

### Filling Inherited Slots

A derived component fills an inherited untyped slot or collection slot with `<<` at its root.
The assignment becomes the slot's default content: the slot stays open, and callers of the derived component can replace it.
Assigning `{ }` removes the inherited default and also leaves the slot open.

```slint
component Base inherits Rectangle {
    slot content << Text { text: "Base default"; }
    VerticalLayout {
        content { }
    }
}

component Derived inherits Base {
    content << Text { text: "Derived default"; }
}

export component App inherits Window {
    VerticalLayout {
        Derived { }   // shows "Derived default"
        Derived {
            content << Text { text: "Caller"; }
        }
    }
}
```

Don't redeclare an inherited slot or place it again in the derived component.
The slot keeps the position its base component gives it.

## Referencing a slot

The name bound to a scalar slot is a regular element reference, so its properties can be read like any other element.

```slint no-test
export component App inherits Rectangle {
    Base {
        header << Rectangle { height: 8px; }
        out property <length> header-y: header.absolute-position.y;
    }
}
```

## Forwarding a slot

A component can forward one of its own slots to a slot of a child component, again with the `<<` operator.
This lets a wrapper expose a nested component's slots as its own.

```slint
export component SlotHost inherits Rectangle {
    slot host-header;
    VerticalLayout {
        host-header {}
        @children
    }
}

export component Outer inherits Rectangle {
    slot header;
    SlotHost {
        host-header << header;   // forward Outer's `header` into SlotHost's `host-header`
        @children
    }
}
```

## Full example

```slint
export component Card inherits Rectangle {
    slot header;
    slot footer;

    VerticalLayout {
        header {}
        @children
        footer {}
    }
}

export component App inherits Window {
    Card {
        header << Text { text: "Title"; }
        Text { text: "Body content"; }
        footer << Text { text: "Footer"; }
    }
}
```

## Typed Slots

Declare `slot <InterfaceName> name;` when a component needs to interact with supplied content through an [interface](./interface).

The host can bind interface inputs, read outputs, modify `in-out` properties, call public functions, and connect callbacks.
Members outside the interface aren't available through the host's slot reference.

```slint
interface Action {
    in property <bool> enabled;
    callback activated();
}

component ActionHost inherits Rectangle {
    in property <bool> enabled: true;
    callback activated();

    slot <Action> action;
    action {
        enabled: root.enabled;
        activated => { root.activated(); }
    }
}

component PointerAction {
    in property <bool> enabled;
    callback activated();

    Text { text: "Click me"; }
    TouchArea {
        enabled: root.enabled;
        clicked => { root.activated(); }
    }
}

export component App inherits Window {
    width: 200px;
    height: 80px;

    ActionHost {
        action << PointerAction { }
        activated => { debug("Activated"); }
    }
}
```

The supplied component must provide the interface's members with matching types, visibility, and function signatures.
Pure interface functions require pure implementations.
An explicit `implement` declaration isn't required.
Members can be declared directly, inherited, or delegated with `implement Action <=> child`.

A typed slot requires exactly one component when its host is instantiated.
A derived component can leave the slot open for its caller.
Unlike an untyped slot, a typed slot that a derived component fills is closed to that component's callers.
When forwarding between two typed slots, both must declare the same interface.

Typed placeholders accept property bindings, callback connections, and property change handlers, but not child elements or new declarations.
Defining handlers for the same callback in both the placeholder and supplied component is an error.
Property bindings follow the existing priorities; more local bindings take precedence.

## Collection Slots

Declare `slot <[implements Entry]> entries;` to accept multiple components that implement an interface.
Enable both `named-slots` and `interfaces` to run the interface-based examples.
Collection slots support three constraints:

| Declaration | Accepted Children |
| --- | --- |
| `slot <[*]> entries;` | Any component, without an interface requirement. |
| `slot <[implements Entry]> entries;` | Any component satisfying the `Entry` interface. |
| `slot <[Entry]> entries;` | The component or built-in element type `Entry`, including components inheriting it. |

An unrelated component with matching properties doesn't satisfy a component type constraint.
An interface constraint doesn't require explicit `implement` declarations.
Wildcard entries expose the standard element properties; typed entries also expose their constraint's public members.

The `default` qualifier routes ordinary children into the collection instead of `@children`.
Fill named collections with repeated assignments such as `entries << EntryView { }`.
A component can declare multiple collection slots, including one default collection.

### Placing Supplied Entries

Enable `named-slots` to run this example.
`ItemGroup` places its supplied children in a vertical layout and exposes their count.
Supply the children individually or use a single `for` loop to create one child per model row.

```slint
import { Button } from "std-widgets.slint";

component ItemGroup {
    default slot <[*]> items;
    out property <int> count: items.length;

    VerticalLayout {
        for item in items: item { }
    }
}

export component App inherits Window {
    in-out property <[string]> labels: ["One", "Two"];

    VerticalLayout {
        padding: 12px;
        spacing: 6px;

        Text { text: "Static entries: \{group.count}"; }
        group := ItemGroup {
            Text { text: "One"; }
            Text { text: "Two"; }
        }

        Text { text: "Model-backed entries: \{model-group.count}"; }
        model-group := ItemGroup {
            for label in root.labels: Text { text: label; }
        }

        Button {
            text: "Add an Entry";
            clicked => { root.labels.push("New entry"); }
        }
    }
}
```

The first group always has two entries.
The second group starts with two entries from `labels`.
Click **Add an Entry** to append a row and see the second group gain a child and update its count.

### Collection Defaults

Collections follow the same default-content rules as named slots.
The declaration can provide one default element; a derived component can provide several default entries.
Omitting an assignment keeps the default; supplying entries replaces the whole default list, and `entries << { }` clears it.
All entries supplied at the same inheritance level form one list.
Entries supplied by a derived component become defaults that its callers can replace or clear.
For a default collection, ordinary children in the derived component also form its default list.
References to default entries must stay inside that default content, as with other named slots.

### Binding Entry Properties

Expand the supplied components with `for`, applying bindings and callback handlers to each component:

```slint
interface Entry {
    in property <int> position;
    in property <bool> selected;
    callback activated();
}

component EntryGroup {
    in-out property <int> current-index: -1;
    out property <int> count: entries.length;
    default slot <[implements Entry]> entries;

    HorizontalLayout {
        for entry[index] in entries: entry {
            position: index;
            selected: index == root.current-index;
            activated => { root.current-index = index; }
        }
    }
}
```

The expansion places existing supplied components without replacing their type or visuals.
The child and optional index variables are available only inside the expansion.
`entries.length` tracks the number of supplied components, including changes to a supplied repeater's model.
Collection lengths and indexes are read-only.
Supply entries as individual components or a single `for` loop.
To include an entry conditionally, use a `for` loop over a model with zero or one row.

Property bindings on a supplied component take precedence over bindings from the expansion.
Property change handlers from both sides are combined.
Defining handlers for the same callback in both the expansion and supplied component is an error.

### Generating Views

Use a component type after the colon to create a separate view for each supplied component.
The loop variable exposes the supplied component's members allowed by the collection constraint.
Property visibility and directions apply as for named element references.
The reference is scoped to the loop and can't be stored in properties or models.
The collection still requires one placement expansion or forwarding assignment.

```slint
interface Page { in property <string> title; }

component Pages {
    in-out property <int> current-index;
    default slot <[implements Page]> pages;
    VerticalLayout {
        HorizontalLayout {
            for page in pages: Text { text: page.title; }
        }
        Rectangle {
            for page[index] in pages: page {
                visible: root.current-index == index;
            }
        }
    }
}
```

Views read the actual component's properties, so changes to a title update its view.
Views support static collection children or a single supplied `for` loop.
For repeated children, each view references the supplied component instance at its row, including after model edits.
Views hold weak references to their supplied instances; removing an entry doesn't retarget an existing view to another entry.
Once the instance is destroyed, writes and calls have no effect.
Property reads and calls with return values return the type's default value.

### Reading an Entry by Index

Use `entries[index].property` to read an exposed property outside a collection loop.
For model-backed entries, the read follows the entry currently at that index after edits to the model.
An out-of-bounds index returns the property's type default.
Indexed access is read-only and exposes individual properties.

```slint
import { Button } from "std-widgets.slint";

component ItemGroup {
    default slot <[Text]> items;
    in property <int> selected-index;
    out property <string> selected-title: items[root.selected-index].text;

    VerticalLayout {
        for item in items: item { }
    }
}

export component App inherits Window {
    in-out property <int> selected-index: 0;

    VerticalLayout {
        padding: 12px;
        spacing: 6px;

        group := ItemGroup {
            selected-index: root.selected-index;
            Text { text: "One"; }
            Text { text: "Two"; }
        }

        Text { text: "Selected: \{group.selected-title}"; }
        Button {
            text: "Next Index";
            clicked => {
                root.selected-index = root.selected-index == 2 ? 0 : root.selected-index + 1;
            }
        }
    }
}
```

Click **Next Index** to cycle through indices 0, 1, and 2.
There are only two entries, so index 2 is out of range and `selected-title` is an empty string.

### Composing Collections

An expansion can supply the default collection of another component:

```slint
component InnerContainer {
    default slot <[*]> content;
    for child in content: child { }
}

export component OuterContainer {
    default slot <[*]> entries;
    InnerContainer {
        for entry in entries: entry { }
    }
}
```

The inner container applies its expansion bindings and layout to the supplied components.
If both expansions bind the same property, the outer expansion's binding takes precedence.
Generated views can also supply another component's default collection.
The target's interface or component constraint still applies, and conflicting callback handlers produce errors.
Lengths and indexes remain those of the supplied collection, including through multiple containers.

The expansion must be the target collection's only child.
The target can generate views of the supplied components, including when its input consists of generated views.
Use the expansion body to add bindings or callback connections before passing the components to the target.

### Forwarding Collections

Forward a collection with the same `<<` syntax as other named slots:

```slint
component ListHost {
    slot <[*]> items;
    out property <int> length: items.length;
    VerticalLayout { for item in items: item { } }
}

component Wrapper {
    default slot <[*]> content;
    out property <int> length: content.length;
    ListHost { items << content; }
}
```

Forwarding counts as the collection's placement; don't also place it with a loop.
Both the wrapper and receiver can generate views of the same entries.
Lengths, indexes, bindings, and component identity are preserved through forwarding chains.
Entries must satisfy both collections' constraints.

Omitting content keeps the receiver's defaults; an explicit empty assignment clears them.
Set defaults on the receiver, as with other forwarded slots.
A forwarded repeater with an empty model stays empty.
Unlike forwarding, a placement loop supplies a list explicitly, so an empty loop removes the receiver's defaults.

### Collection Limits

- Each collection requires exactly one placement expansion or forwarding assignment; additional loops can generate views.
- Expansions accept bindings, two-way bindings, callback connections, and property change handlers, but no child elements or member declarations.
- Supply static components or a single `for` loop; conditional children and mixtures of static children and repeaters aren't supported.
- Place collection expansions outside `ListView` itself.
  Use a model loop for virtualized delegates.
  Each delegate can contain components that use collection slots.
- Generate views and read properties by index from static entries or a non-virtualized source repeater.
- Forwarding `@children` into collections isn't supported; declare a default collection slot to forward ordinary children.

`@children` remains supported separately; collection slots don't yet replace its forwarding behavior.

## Current limitations

The named slot feature is in its early stages. The following restrictions apply:

- The name `children` is reserved for the default slot. Use `@children`, or declare a default collection slot.

- A slot must be rendered exactly once, and it may not be placed inside a `for`, `if`, or `match` element.

- A collection slot must be rendered by a `for` loop.

- A slot cannot be placed inside a `PopupWindow` or a `ComponentContainer`.

- Slot assignment and forwarding are only valid on components, and each scalar slot may be assigned at most once.
