In the following sections, we provide you with lessons we've learned of the years. This will help you avoid some pitfalls, tricky situations, and improve maintainability of your UI code.

## Accessibility

When designing custom components, consider early on to declare <Link type="AccessibleProperties" label="accessibility properties" />. At least a role, possibly a label, as well as actions.

If you're developing on Windows, then [Accessibility Insights](https://accessibilityinsights.io/docs/windows/overview/) tool for windows is a great tool to help you find and fix accessibility issues.

If you're developing on macOS, the [Accessibility Inspector](https://developer.apple.com/documentation/accessibility/accessibility-inspector) offers similar functionality. Note that it requires the application to be built as bundle.

```slint
component CustomButton {
    // ...
    in property <string> text;

    accessible-role: button;
    accessible-label: self.text;
    accessible-action-default => { /* simulate click */ }
}
```

## Separate Code, UI, and Assets

Many projects start out small, with just a few files. But before you know it, your team grows, files get added, and it becomes harder to see forest for the trees. We recommend starting with the following basic directory structure:

```
my-project
├── src
│   ├── main.cpp / main.rs / main.js / main.py
│        <this is where your main business logic lives>
├── ui
    ├── app-window.slint <the entry point for your Slint UI>
    ├── <additional .slint files here>
    ├── images
        ├── logo.svg
        ├── highlight-marker.svg
        ├── <all your images go here>

```

## Translations

* When adding user-visible strings to your UI, consider early on to mark them as <Link type="translations" label="translatable" /> by wrapping them in `@tr("...")`.
* Avoid `+` for concatenating strings, prefer `{}` substitutions. This gives translators the option of re-ordering the arguments for the most natural translation.

<Aside type="caution">

```slint
export component Example {
    property <string> name;

    Text {
        text: "Ink Level Controls"; // Oooops, forgot to mark as translatable
    }
    Text {
        text: @tr("Hello, ") + name; // Oooops, this is difficult to translate
    }
}
```

</Aside>

<Aside type="tip">

```slint
export component Example {
    property <string> name;

    Text {
        text: @tr("Ink Level Controls");
    }
    Text {
        text: @tr("Hello, {}", name); // Good, now the translator can re-order
    }
}
```

</Aside>

## Performance

When creating a Slint app, performance can become an issue as scenes get more complex.
This is most noticeable on low-end hardware.
Below are some things you can look out for based on the renderer being used.

### General
- Opacity on an element with multiple children renders to an offscreen layer in Skia and FemtoVG.
  Put opacity on the children if they don't overlap instead.
- <Link type="drop-shadows" label="Drop shadows" /> are expensive when redrawn.
  Skia and FemtoVG cache at most 16 distinct shadows and modifying any of the following properties creates a new cache entry:
    - geometry
    - color
    - blur
    - radius
    - spread
    - inset (along with offsets on inset shadows)
    - background (only counts for non-inset shadows)
    - border (only counts for non-inset shadows)
    - scale factor
- SVG images are expensive to rasterize.
  Skia and FemtoVG cache the results, and the software renderer recomputes the images on a redraw.
  The following properties invalidate the cache:
    - source
    - colorize
    - image-fit
    - width/height

### Partial Renderer
- Partial rendering is only supported in the software and Skia software renderers.
- At most 3 dirty rectangles are redrawn every frame.
  Rectangles get merged when more than 3 objects are dirty at a time.
  This can result in more of the screen being redrawn than expected.
  Keep changing elements close together.
- Animations mark regions dirty every frame, so expensive elements can be redrawn more than expected.

### FemtoVG
- Rounded clips (`border-radius` with `clip: true`) render into an offscreen layer which is cached.
  This can be expensive, especially when animated objects invalidate the cache every frame.

### Skia
- Backdrop blur is slow on the CPU as it has to resample everything behind the rectangle and blur it.

### Software
- Radial and conic gradients are slow on MCUs without an FPU.
  Pre-generate them into opaque images at the displayed size.
- Scaling images is slow. Store images as the size they are displayed as.
- Blending pixels is slow. Try to avoid translucency on large surfaces.
- SVG images and paths are expensive as they are recomputed every time they are drawn.
