A `slint-project.json` file holds the main file and compiler settings of a project, such as include paths.
Your build and your editor both read it, so they compile your `.slint` files the same way.

## Location

When Slint compiles a `.slint` file, it looks for `slint-project.json` in the directory of that file
and then in each parent directory.
It uses the first one it finds and ignores any further up.
For example, compiling `/projects/app/ui/main.slint` checks these paths in order:

- `/projects/app/ui/slint-project.json`
- `/projects/app/slint-project.json`
- `/projects/slint-project.json`
- `/slint-project.json`

Place the file next to a `.slint` file to configure a single UI,
or in the root of your repository to configure all of them.

## Example

```json
{
    "slint-edition": "1.19",
    "main": "ui/main.slint",
    "include-paths": ["ui/shared"],
    "library-paths": {
        "widgets": "ui/widgets"
    }
}
```

The file is JSON with `//` and `/* */` comments.
Every setting is optional, except `slint-edition`.

## Settings

| Setting | Type | Description |
|---------|------|-------------|
| `slint-edition` | string | Required. The Slint release whose language behavior to use, such as `"1.19"`. See [Edition](#edition). |
| `include-paths` | array of strings | Directories to search for imported `.slint` files. |
| `library-paths` | object | Maps a library name to a file or directory, for `@library` imports. |
| `enable-experimental-features` | boolean | Turns on features that aren't stable yet. |
| `main` | string | The `.slint` file to compile when you pass the project file itself. See [Compiling the Project File](#compiling-the-project-file). |

Relative paths are resolved against the directory that contains the project file.

## Edition

Set `slint-edition` to the Slint release you write your project for, as major and minor version.
Write it as a string: `"1.19"`, not `1.19`.
Use the version of Slint you build with, or any older one.

When a Slint release changes the behavior of the language,
the change applies only to projects that target that release or a newer one.
A newer Slint keeps compiling your project the way the targeted release did,
until you raise the edition.
New features don't depend on the edition: use them with any edition.
A Slint older than the edition refuses to compile the project.

Without a project file, Slint uses the behavior from before Slint 1.19.

These releases changed the behavior:

- 1.19: An element created with `if` or `for` counts toward the size of its parent,
  as a static child does ([#407](https://github.com/slint-ui/slint/issues/407)).
  A child that sizes itself from that parent then forms a binding loop, which the compiler reports as an error.
  To fix it, size the child without reading the parent's size:
  - Replace `width: parent.width` with `width: 100%`, and the same for `height`.
    Don't do this for an element placed in a layout: there, a percentage is an exact demand on the layout.
  - Remove a size computed from the parent's size minus some padding when a layout already applies that padding and spacing.
  - Give the parent an explicit `width` or `height`.
  - As a last resort, set `x` or `y` on the child, which keeps it out of its parent's size.
    This pins its position: a `Text` that was centered in its parent moves to `0, 0`.
    In a layout, where setting `x` is an error, wrap the child in a `Rectangle` and set `x` on that.

## Which Setting Wins

A setting can come from three places.
From highest to lowest priority:

1. An option passed to the API or the command line, such as an include path.
2. The project file.
3. A compiler default.

`slint-edition` comes only from the project file.

## Compiling the Project File

Set `main` to the main `.slint` file of your application,
then pass the project file wherever a `.slint` file is expected.
Slint compiles the main file with the settings of that project file and doesn't look for another one.

```json
{
    "slint-edition": "1.19",
    "main": "ui/main.slint"
}
```

The command line compiler accepts it too: `slint-compiler slint-project.json -o main.h`.

## Usage

Every way of compiling a `.slint` file reads the project file, without any setup.

<Tabs syncKey="dev-language">
<TabItem label="Rust" icon="seti:rust">
`build.rs` and the `slint!` macro both read the project file.
Settings on <LangRefLink lang="rust-slint-build" relpath="struct.CompilerConfiguration">`CompilerConfiguration`</LangRefLink> win over it.
Cargo rebuilds your crate when the project file changes.

```rust
// build.rs
fn main() {
    // Uses ui/slint-project.json, or the nearest one above it.
    slint_build::compile("ui/main.slint").unwrap();
}
```

The `slint!` macro starts the search in the directory of its `.rs` file.
</TabItem>
<TabItem label="C++" icon="seti:cpp">
<LangRefLink lang="cpp" relpath="cmake-reference/slint-target-sources/">`slint_target_sources`</LangRefLink> reads the project file,
and CMake rebuilds your target when the project file changes.

```cmake
slint_target_sources(my_application ui/main.slint)
```

The interpreter reads it too, when you load a `.slint` file at run time.

The `SLINT_STYLE` CMake variable is passed to the compiler as `--style`.
</TabItem>
<TabItem label="NodeJS" icon="node">
<LangRefLink lang="nodejs" relpath="api/functions/loadFile/">`loadFile`</LangRefLink> reads the project file.
The options you pass win over it.

```javascript
import * as slint from "slint-ui";

// Uses ui/slint-project.json, or the nearest one above it.
let ui = slint.loadFile("ui/main.slint");
```
</TabItem>
<TabItem label="Python" icon="seti:python">
Loading a `.slint` file reads the project file.
The arguments you pass win over it.

```python
import slint

# Uses ui/slint-project.json, or the nearest one above it.
class MainWindow(slint.loader.ui.app.AppWindow): ...
```
</TabItem>
</Tabs>

## Editor Support

The Slint language server and the live preview read the project file too,
so your editor resolves imports the same way your build does.
They reload it when it changes.
