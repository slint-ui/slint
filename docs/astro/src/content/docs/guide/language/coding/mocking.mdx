---
title: Mocking Data
description: Populating your UI with placeholder data while designing, without shipping it in the compiled application.
---

While designing a UI, it's useful to see it filled with realistic-looking data before any business
logic exists to provide it. Slint offers two building blocks for this: `Platform.uses-mock-data`
tells you whether the `.slint` file is running on its own, and `@from-json(...)` loads values from
a JSON file at compile time. Combined, they let you preview a fully populated UI while keeping the
compiled application free of placeholder data.

## `Platform.uses-mock-data`

`Platform.uses-mock-data` is `true` when the `.slint` file is being previewed on its own — for
example with `slint-viewer` or an editor's live preview — and `false` once it's driven by a host
application written in Rust, C++, JavaScript, or Python. It's a compile-time constant, so any
branch that depends on it is optimized away once the value is known, meaning mock data never ends
up in your compiled application.

```slint
import { ListView, VerticalBox } from "std-widgets.slint";

export struct Contact {
    name: string,
    online: bool,
}

export component Example inherits Window {
    width: 150px;
    height: 150px;

    in property <[Contact]> contacts: Platform.uses-mock-data ? [
        { name: "Alice", online: true },
        { name: "Bob", online: false },
        { name: "Carol", online: true },
    ] : [];

    VerticalBox {
        ListView {
            for contact in root.contacts : Rectangle {
                height: 24px;
                Text {
                    text: contact.name;
                    color: contact.online ? green : gray;
                }
            }
        }
    }
}
```

Once a host application sets `contacts` itself, `Platform.uses-mock-data` is `false`, the ternary's
first branch is compiled out, and the placeholder data never ships.

## `@from-json(...)`

Typing placeholder values directly into a `.slint` file works for a couple of rows, but gets
unwieldy for anything larger, and can't be shared with a designer or generated by a script.
`@from-json("file.json")` reads a JSON file at compile time instead, looking up a value whose key
matches the name of the property it's assigned to:

```slint
export component Example {
    // Looks up the "greeting" key at the root of the JSON file
    property <string> greeting: @from-json("data.json");
}
```

`@from-json("file.json", "path/to/value")` takes a `/`-separated path to look up a nested value:

```slint
export component Example {
    property <int> count: @from-json("data.json", "stats/visitors/count");
}
```

The JSON value is converted to match the property's declared type — including arrays and structs,
recursively — so a JSON file can describe entire lists of mock records, not just scalars. Both
arguments must be plain string literals, since the file is read once, at compile time; see the
[`@from-json`](../../../../reference/language/expressions/#from-json) reference for the full
conversion and lookup rules.

## Combining both

The two are usually used together: `@from-json(...)` supplies realistic mock data, and
`Platform.uses-mock-data` makes sure that data is only loaded while previewing, not in the
compiled application. Because a conditional expression always needs an else branch, give it a
sensible empty default for the real application:

```slint
export struct Contact {
    name: string,
    online: bool,
}

export component Example {
    in property <[Contact]> contacts: Platform.uses-mock-data ? @from-json("contacts.json") : [];
}
```

Until a host application sets `contacts`, the preview shows the data from `contacts.json`. Once
it's compiled into a real application, `Platform.uses-mock-data` folds to `false`, the `@from-json`
call is compiled out together with the branch that contains it, and nothing about `contacts.json`
ends up in the final binary.
