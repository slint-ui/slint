## Safety Policy

The safety and quality of Slint SC are the primary objectives of all management, development, maintenance and support activities.

Each commitment names where it's implemented, so it can be checked rather than taken on trust.

* Every change follows a defined process. See [Development Process](/safety-plan/development-process/) and [Development Phases](/safety-plan/development-phases/).
* Every change is verified by automated tests before it's merged. See [Test Suites](/safety-plan/test-suites/).
* Every requirement is traced to the tests that verify it. See [Traceability Matrix](/qualification-report/traceability-matrix/).
* Known safety-critical problems are recorded, with the fix and the test that covers each. See [Known Problems](/user-manual/known-problems/).
* The process and the tooling are improved as we go, and what can be automated is automated.

## Roles and Responsibilities

**Addresses:** ISO 26262-2 6.4.2

The administrators of the slint-ui GitHub organization are the founders of SixtyFPS GmbH.
All employees of SixtyFPS GmbH are members of the organization.
External contributors may also be invited to become members of the GitHub organization.

One person can hold several roles, as long as the independence of each [confirmation measure](#confirmation-measures) holds.
Who holds each role is recorded internally.

| Role | Responsible for |
| --- | --- |
| Project Manager | Resources, schedule, and compliance with ISO 26262 |
| Safety Manager | This Safety Plan and its tailoring, tracking progress against it, the safety case, and scheduling the confirmation measures |
| Technical Lead, Runtime | Software requirements, architecture, and implementation of the runtime |
| Technical Lead, Compiler | The `--slint-sc` mode of the compiler, and `slint-sc-coverage` |
| Verification Lead | Test strategy, test suites, coverage, and traceability |
| Release Manager | Branches, tags, baselines, and release artifacts |
| Confirmation Reviewer | The confirmation reviews below |
| Functional Safety Auditor | The functional safety audit |
| Functional Safety Assessor | The functional safety assessment, by TÜV Nord |
| Release Authority | Signing the release report |
| Field Monitoring Owner | Taking in anomaly reports after a release, and notifying integrators |

The Safety Manager can block a release.

## Confirmation Measures

**Addresses:** ISO 26262-2 6.4.9 to 6.4.12

Confirmation measures check that the work products, the process, and the resulting safety are adequate.
Each one needs a level of independence from the people who did the work, which depends on the ASIL.
At ASIL B, ISO 26262-2 Table 1 asks for:

* **I0:** should be done; if done, by someone other than the author.
* **I1:** must be done, by someone other than the author.

Table 1 has no ASIL B entry for the impact analysis or the hazard analysis, because neither applies; see [Tailoring](/safety-plan/standards-compliance/#tailoring).

| Measure | Independence at ASIL B | Performed by | When |
| --- | --- | --- | --- |
| Confirmation review of this Safety Plan, including its tailoring | I1 | Confirmation Reviewer | Before the first release, then in any release that revised the plan |
| Confirmation review of the verification strategy | I1 | Confirmation Reviewer | Before the first release, then when [Verification](/safety-plan/verification/) changes |
| Confirmation review of the safety analyses | I1 | Confirmation Reviewer | Before the first release, then in any release that changed them |
| Confirmation review of the safety case | I1 | Confirmation Reviewer, not the Safety Manager | Every release |
| Functional safety audit | I0 | Functional Safety Auditor | Before the first release, early enough to fix findings, then once a year |
| Functional safety assessment | I0 | TÜV Nord | A full assessment for the first release; for later ones, an assessment of what changed |

The audit and the assessment are only recommended at ASIL B, by ISO 26262-2 6.4.11.1 and 6.4.12.1.
We do both, since the TÜV Nord certificate rests on the assessment.

Each confirmation report names the work products it covers and their versions.
The reviews and the audit due for a release finish before that release.
