**Addresses:** ISO 26262-2 6.4.6

The Safety Plan lists the safety activities of Slint SC.
For each activity, the plan states the objective, the role responsible, when the activity happens, and what the activity produces.
Where an activity is already described elsewhere in this manual, the plan links to it rather than repeating it.

What can go wrong, and what we do about it, is in the [Tool Evaluation Report](/evaluation-report/) and the [Component Documentation](/component-documentation/).
The evidence from running the tests is in the [Qualification Report](/qualification-report/).

## How Slint SC Is Developed

SixtyFPS GmbH delivers Slint SC to integrators as a software component.
They build it into their own products, at up to ASIL B.
We don't build a product ourselves, so there's no vehicle function or hardware on our side.
The integrator builds the product and certifies it.

Slint SC consists of tools and a runtime, and each takes its own route through ISO 26262:

* The `slint-sc` runtime ships in the integrator's binary.
  It's developed under ISO 26262-6 as a Safety Element out of Context: a component developed before anyone knows which product it goes into.
  See [Tailoring](/safety-plan/standards-compliance/#tailoring) for what that changes.
* The Slint compiler in `--slint-sc` mode and `slint-sc-coverage` don't ship.
  They're tools, covered by ISO 26262-8 Clause 11 in the [Tool Evaluation Report](/evaluation-report/).

The runtime isn't qualified under ISO 26262-8 Clause 12, which is meant for existing software reused without re-engineering.

## Release Scope

Each release states the language subset and the runtime features it covers, and the compiler rejects everything else.
The subset is what the [Reference](/reference/) lists.
Extending it is a change like any other.
